[2026-11-11] ETAPE 1 - Préparation des disques externes (effacement + ext4)
--------------------------------------------------------------------------
But : remplacer NTFS (format Windows, mal adapté aux permissions Linux et
à Docker) par ext4, le format standard de Linux.
Principe : table de partitions (GPT) -> partition -> système de fichiers.
ATTENTION : sdb/sdc ne sont pas des noms fixes (ordre de branchement).
Toujours vérifier avec lsblk avant toute commande destructrice.

sudo apt update && sudo apt install -y parted
    -> met à jour la liste des paquets puis installe parted (outil de
       partitionnement, absent de l'installation de base).

lsblk -o NAME,SIZE,MODEL
    -> liste les disques pour identifier lequel est lequel
       (sdc = Crucial X9 CT1000X9SSD9, sdb = Samsung 860 EVO ex-PS4).

sudo wipefs -a /dev/sdc
sudo wipefs -a /dev/sdb
    -> efface toutes les signatures (anciennes partitions NTFS/Windows) :
       les disques apparaissent vierges.

sudo parted /dev/sdc --script mklabel gpt mkpart medias ext4 0% 100%
sudo parted /dev/sdb --script mklabel gpt mkpart telechargements ext4 0% 100%
    -> crée une table GPT et une partition unique sur tout le disque.
       0%-100% laisse parted aligner la partition (performances SSD).

sudo mkfs.ext4 -L medias -m 0 /dev/sdc1
sudo mkfs.ext4 -L telechargements -m 0 /dev/sdb1
    -> formate en ext4. -L = étiquette lisible. -m 0 = supprime les 5 %
       réservés à root (inutiles sur un disque de données, ~46 Go gagnés).

lsblk -o NAME,SIZE,FSTYPE,LABEL,MODEL
    -> contrôle du résultat.

Résultat : OK, aucune erreur.
  sdc1  ext4  LABEL=medias           UUID=7bf0403a-19e4-4cdc-bb40-75e0f61429fa
  sdb1  ext4  LABEL=telechargements  UUID=efb2dae1-d63e-4094-bb76-270c5488990e

Anomalie mineure : le NOM DE PARTITION GPT (PARTLABEL) de sdb1 est "medias"
au lieu de "telechargements" (commande parted probablement lancée deux fois).
Sans conséquence : c'est l'étiquette ext4 (LABEL) et l'UUID qui servent.
Correction facultative :
  sudo parted /dev/sdb --script name 1 telechargements

[2026-11-11] ETAPE 2 - Montage automatique des disques (/etc/fstab)
--------------------------------------------------------------------------
Principe : sous Linux, un disque est "accroché" sur un dossier vide
(point de montage). /etc/fstab liste les montages faits à chaque démarrage.
On désigne les disques par UUID (fixe), jamais par sdb/sdc (variables).

sudo mkdir -p /mnt/medias /mnt/telechargements
    -> crée les deux points de montage.

sudo cp /etc/fstab /etc/fstab.bak
    -> sauvegarde de fstab avant modification (une erreur peut bloquer
       le démarrage).

echo 'UUID=7bf0...  /mnt/medias  ext4  defaults,noatime,nofail,x-systemd.device-timeout=10s 0 2' | sudo tee -a /etc/fstab
echo 'UUID=efb2...  /mnt/telechargements  ext4  (mêmes options)  0 2' | sudo tee -a /etc/fstab
    -> ajoute les deux lignes en fin de fstab. "sudo tee -a" car une
       redirection ">>" ne serait pas exécutée en root.
    Options :
      noatime  = n'écrit pas la date de chaque lecture (moins d'usure SSD)
      nofail   = le système démarre même si le disque USB est absent
      x-systemd.device-timeout=10s = n'attend le disque que 10 s
      0 2      = pas de dump ; vérification fsck après le disque système

sudo findmnt --verify
    -> vérifie la syntaxe de fstab sans rien monter.

sudo systemctl daemon-reload
sudo mount -a
    -> systemd relit fstab, puis tout ce qui est listé est monté.

sudo chown saaos:saaos /mnt/medias /mnt/telechargements
    -> donne les disques à l'utilisateur saaos (au lieu de root) :
       les conteneurs tourneront sous cette identité (moindre privilège).

sudo parted /dev/sdb --script name 1 telechargements
    -> corrige le nom de partition GPT du Samsung (anomalie de l'étape 1).

Résultat : OK, aucune erreur.
  /dev/sdc1 -> /mnt/medias           916 Go dispo, rw,noatime
  /dev/sdb1 -> /mnt/telechargements  916 Go dispo, rw,noatime
Remarque : l'option "stripe=8191" apparaît sur le Samsung. Elle vient du
boîtier USB "Essentiel B" qui déclare une taille d'écriture optimale
inhabituelle. ext4 l'a prise en compte au formatage. Sans conséquence.
Test de redémarrage : à faire après l'étape 3.

[2026-11-11] ETAPE 4 - Adresse IP fixe (bail DHCP statique sur la Livebox)
--------------------------------------------------------------------------
But : le serveur garde toujours la même adresse locale, indispensable
pour la redirection de ports (accès depuis internet) faite plus tard.

Principe : DHCP = service de la box qui prête automatiquement une
adresse IP à chaque appareil, pour une durée limitée (le "bail").
Un bail statique associe définitivement une IP à une adresse MAC
(identifiant physique de la carte réseau).
Choix : réservation côté box plutôt qu'IP fixe écrite dans Debian
-> plus simple, et pas de risque de conflit avec une adresse que la
box distribuerait à un autre appareil.

ip link show enx0050b6cd50ce
    -> affiche l'adresse MAC de l'adaptateur Ethernet du dock (après
       "link/ether") : 00:50:b6:cd:50:ce
       (le nom "enx..." de l'interface est d'ailleurs construit à
       partir de cette MAC).

Interface web de la Livebox (http://192.168.1.1), menu Réseau / DHCP :
    -> bail statique ajouté : MAC 00:50:b6:cd:50:ce -> 192.168.1.28

Côté Debian, rien à changer : /etc/network/interfaces garde
"iface enx0050b6cd50ce inet dhcp" (gestionnaire ifupdown) ; c'est la
box qui renverra toujours la même adresse.
Contrôle : 192.168.1.28/24, passerelle 192.168.1.1. OK.

[2026-11-11] ETAPE 5 - Installation de Docker (dépôt officiel)
--------------------------------------------------------------------------
Principe : image = modèle d'application téléchargé ; conteneur = copie
de l'image en fonctionnement, isolée du système. docker compose décrit
tous les conteneurs dans un fichier texte (compose.yaml).
Choix du dépôt officiel Docker plutôt que le paquet Debian "docker.io" :
version à jour et plugin "docker compose" (v2).

sudo apt install -y ca-certificates curl
    -> curl (téléchargement) + certificats racine (vérification HTTPS).

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
    -> crée le dossier des clés de dépôts, télécharge la clé de
       signature de Docker et la rend lisible par apt. Grâce à elle,
       apt refuse tout paquet qui ne serait pas signé par Docker.

sudo nano /etc/apt/sources.list.d/docker.sources
    -> déclare le dépôt (format "deb822", un champ par ligne) :
         Types: deb
         URIs: https://download.docker.com/linux/debian
         Suites: trixie
         Components: stable
         Architectures: amd64
         Signed-By: /etc/apt/keyrings/docker.asc

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
    -> moteur Docker (service), commande docker, containerd (lance
       réellement les conteneurs), buildx (construction d'images),
       plugin compose.

sudo docker run --rm hello-world
    -> test : télécharge une image minuscule, la lance, supprime le
       conteneur (--rm). Message "Hello from Docker!" = OK.

sudo usermod -aG docker saaos
    -> ajoute saaos au groupe docker (-a = ajouter sans retirer les
       autres groupes) pour utiliser docker sans sudo.
       SECURITE : appartenir au groupe docker = équivalent root
       (Docker peut monter n'importe quel dossier). Acceptable car
       utilisateur unique ; ne jamais l'accorder à un tiers.
    -> déconnexion / reconnexion SSH : les groupes ne sont lus qu'à
       l'ouverture de session.

Vérifications (OK) :
  - Docker 29.9.3, Docker Compose v5.7.0
  - services docker et containerd : enabled (démarrent au boot), active
  - stockage : overlayfs, dossier /var/lib/docker (SSD système ADATA)
  - cgroup driver systemd ; journaux des conteneurs : json-file
Observation : une session ouverte AVANT le usermod (ici celle de Claude
Code) obtient "permission denied ... docker.sock". Normal : il faut une
nouvelle session (ou "sg docker -c '...'" pour tester ponctuellement).
Suite (2026-11-11) : session SSH rouverte par l'utilisateur -> "docker ps"
fonctionne désormais sans sudo (groupe docker pris en compte). OK.

[2026-11-11] ETAPE 6 - Organisation des dossiers
--------------------------------------------------------------------------
Principe : séparer 3 types de données.
  - la "recette" (compose.yaml, docs)   -> ~/serveur-maison/ (dépôt GitHub)
  - l'état des applis (config, bases)   -> /srv/appdata/<appli>/ (SSD
    système, HORS du dépôt : contient mots de passe/clés, jamais publié)
  - les gros fichiers                   -> /mnt/medias, /mnt/telechargements
/srv = emplacement prévu par Linux pour les données "servies" par la machine.

Problème des deux disques : impossible de faire un lien (hardlink) d'un
disque à l'autre, donc garder un torrent sur le Samsung ET le média sur le
Crucial doublerait la place occupée.
Solution retenue (fonction native de qBittorrent) :
  - téléchargement en cours -> /mnt/telechargements/incomplets (Samsung,
    encaisse les écritures désordonnées)
  - torrent terminé -> déplacé automatiquement vers /mnt/medias/<catégorie>
    (Crucial), le partage (seed) continue depuis là. Une seule copie.
  - non-médias terminés -> /mnt/telechargements/termines
  - Jellyfin / Navidrome lisent /mnt/medias.

mkdir -p /mnt/medias/{films,series,musique}
mkdir -p /mnt/telechargements/{incomplets,termines,sauvegardes}
    -> -p : crée les parents si besoin, pas d'erreur si déjà présent.
       {a,b,c} : expansion d'accolades de bash (3 dossiers en 1 ligne).
       Pas de sudo : disques donnés à saaos à l'étape 2.

sudo mkdir -p /srv/appdata/{gluetun,qbittorrent,jellyfin,navidrome}
sudo chown -R saaos:saaos /srv/appdata
    -> /srv appartient à root, d'où sudo ; puis on donne le tout à saaos
       (-R = récursif). Les conteneurs tourneront en UID 1000 (saaos) :
       principe du moindre privilège.
       Dossier du reverse proxy : créé à son étape.

sudo apt install -y tree
tree -L 1 /mnt/medias /mnt/telechargements /srv/appdata
    -> affiche l'arborescence (1 niveau).

Résultat : OK, aucune erreur.
  - Tous les dossiers appartiennent à saaos:saaos.
  - Droits 775 sous /mnt (créés par saaos, umask 002) et 755 sous
    /srv/appdata (créés via sudo, umask 022 de root). Sans conséquence :
    seul saaos écrit dedans.
  - lost+found (root, 700) présent sur chaque disque : créé par ext4,
    utilisé par fsck pour ranger les fragments récupérés après une coupure.
    NE PAS SUPPRIMER.

[2026-11-11] ETAPE 7 - Tunnel VPN (Gluetun + Proton VPN WireGuard)
--------------------------------------------------------------------------
Principes :
  - WireGuard = protocole VPN à paire de clés. La clé PRIVEE (secret,
    jamais sur GitHub ni dans la conversation) prouve l'abonnement.
    Chez Proton, une même clé fonctionne sur tous les serveurs.
  - Kill switch : qBittorrent n'aura AUCUN réseau propre ; il sera branché
    dans le réseau du conteneur Gluetun, dont le pare-feu bloque tout sauf
    le tunnel. VPN coupé = aucun chemin vers internet.
  - Redirection de port NAT-PMP : Proton ouvre un port côté serveur VPN
    (rien d'ouvert sur la Livebox), Gluetun le récupère.

7.2 Génération de la configuration (account.protonvpn.com > Téléchargements
> Configurations WireGuard) : nom "serveur-maison", plateforme GNU/Linux,
NetShield "malwares", Moderate NAT désactivé, NAT-PMP (Port Forwarding)
ACTIVE, VPN Accelerator activé, serveur suisse P2P.
Seule la ligne "PrivateKey" est utile. Fichier .conf supprimé côté Windows.

7.3 Fichier des secrets
install -m 600 /dev/null ~/serveur-maison/.env
    -> crée un fichier vide déjà en droits 600 (lecture/écriture pour
       saaos seul), AVANT d'y écrire le secret.
nano ~/serveur-maison/.env
    -> une ligne : WIREGUARD_PRIVATE_KEY=<clé>  (sans espace ni guillemet)
       docker compose lit automatiquement .env ; compose.yaml n'y fera
       référence que par ${WIREGUARD_PRIVATE_KEY}.
Vérification (sans afficher la clé) : saaos:saaos 600, 1 ligne, clé de
44 caractères au format base64, pas d'espace/guillemet/retour Windows. OK.

7.4 Fichier .gitignore
nano ~/serveur-maison/.gitignore
    -> contient ".env" : git ignorera ce fichier, le secret ne pourra pas
       être publié sur GitHub par erreur.

7.5 Fichier compose.yaml (service gluetun)
nano ~/serveur-maison/compose.yaml
    Points clés :
      image qmcgaw/gluetun:v3        tag de version majeure (pas de rupture)
      cap_add NET_ADMIN              seul droit réseau accordé (pas root total)
      devices /dev/net/tun           interface tunnel du noyau
      sysctls disable_ipv6=1         IPv6 supprimé dans le réseau de Gluetun
                                     (en plus du blocage par son pare-feu :
                                     défense en profondeur)
      WIREGUARD_PRIVATE_KEY=${...}   valeur lue dans .env
      SERVER_COUNTRIES=Switzerland
      PORT_FORWARD_ONLY=on           uniquement serveurs P2P compatibles
      VPN_PORT_FORWARDING=on         port NAT-PMP demandé et renouvelé
      ports 192.168.1.28:8080:8080   interface web qBittorrent limitée au
                                     réseau local
      restart unless-stopped         redémarre après plantage / reboot
    LECON : les ports publiés par Docker passent AVANT ufw (Docker écrit
    ses propres règles). D'où l'adresse IP précisée devant le port.

7.6 Validation et démarrage
cd ~/serveur-maison
docker compose config --quiet
    -> valide la syntaxe sans rien afficher. ATTENTION : sans --quiet la
       commande affiche la clé privée en clair.
docker compose up -d gluetun
    -> télécharge l'image, crée et démarre le conteneur en arrière-plan.
docker logs -f gluetun
    -> suit le journal en direct (Ctrl+C pour sortir, le conteneur
       continue de tourner).

Résultat : OK, aucune erreur.
  - Conteneur gluetun : Up (healthy)
  - Serveur WireGuard 62.169.136.3:51820
  - IP publique vue d'internet : 62.169.136.54 (Suisse, Zurich)
  - Port redirigé obtenu : 34830 (écrit dans /tmp/gluetun/forwarded_port ;
    il peut changer à chaque reconnexion)
  - IPv6 : disable_ipv6=1 et aucune adresse IPv6 dans le conteneur.
  - Port 8080 publié sur 192.168.1.28 uniquement.
Remarque : le message "Wireguard is a silent protocol..." n'est pas une
erreur, juste un avertissement générique (WireGuard ne signale pas les
échecs ; c'est l'obtention de l'IP publique qui prouve que ça marche).

[2026-11-11] ETAPE 8 - qBittorrent dans le réseau de Gluetun
--------------------------------------------------------------------------
Principes :
  - network_mode: "service:gluetun" : qBittorrent n'a pas de carte réseau
    propre, il partage celle de Gluetun (interface tun0 + pare-feu).
    Son localhost (127.0.0.1) est le même que celui de Gluetun.
  - Gluetun transmet le port NAT-PMP à l'API web de qBittorrent
    (VPN_PORT_FORWARDING_UP_COMMAND + wget), ce qui nécessite l'option
    "Bypass authentication for clients on localhost".
  - VPN coupé : torrents bloqués à 0 ko/s, reprise automatique.
    Conteneur Gluetun arrêté/recréé : qBittorrent perd le réseau jusqu'à
    son propre redémarrage (gênant mais SANS fuite) -> toujours
    "docker compose down" puis "docker compose up -d".
  - 3 protections indépendantes : réseau partagé, pare-feu Gluetun,
    qBittorrent lié à l'interface tun0.

nano compose.yaml
    -> ajout dans gluetun de VPN_PORT_FORWARDING_UP_COMMAND (envoie
       {"listen_port":<port>} à http://127.0.0.1:8080/api/v2/app/setPreferences)
    -> ajout du service qbittorrent : image lscr.io/linuxserver/qbittorrent,
       network_mode service:gluetun, depends_on gluetun "service_healthy",
       PUID/PGID 1000, WEBUI_PORT 8080, volumes /srv/appdata/qbittorrent
       -> /config, /mnt/telechargements -> /telechargements,
       /mnt/medias -> /medias.
docker compose config --quiet
docker compose down
docker compose up -d
    -> down supprime les conteneurs (pas les données de /srv/appdata),
       up recrée tout dans l'ordre (qBittorrent après Gluetun "healthy").
docker logs qbittorrent
    -> récupération du mot de passe temporaire de "admin".

Réglages faits dans l'interface web (http://192.168.1.28:8080) :
  Advanced   : Network interface = tun0, IP de liaison = toutes IPv4
  Connection : UPnP/NAT-PMP du routeur DESACTIVE (ne jamais ouvrir de port
               sur la Livebox)
  Downloads  : enregistrement par défaut /telechargements/termines,
               incomplets dans /telechargements/incomplets
Vérifié dans /srv/appdata/qbittorrent/qBittorrent/qBittorrent.conf : OK.

Test : IP publique vue DEPUIS le conteneur qbittorrent

  -> 79.127.184.193, Zürich, CH : le trafic de qBittorrent sort par le VPN.
  (Serveur différent de l'étape 7 : à chaque recréation, Gluetun choisit
  un serveur suisse P2P au hasard. Normal.)

[2026-11-11] ETAPE 11 - Accès depuis internet : réflexion et DECISION
--------------------------------------------------------------------------
Question de l'utilisateur : pourquoi ne pas tout faire passer par Tailscale,

Analyse :
  - Oui, Tailscale seul = surface d'attaque quasi nulle : aucun port ouvert
    sur la box, serveur invisible pour un inconnu ; protection par ce qu'on
    POSSEDE (appareil inscrit) et non par ce qu'on SAIT (mot de passe).
    "Ne pas exposer vaut mieux que bien exposer."
  - MAIS Android n'autorise qu'UN SEUL VPN actif à la fois. L'utilisateur
    utilise souvent Proton VPN sur son téléphone -> Tailscale seul
    obligerait à basculer Proton/Tailscale à chaque écoute.
  - Le reverse proxy public est un simple site web : accessible À TRAVERS
    Proton VPN, sans conflit.
DECISION : solution HYBRIDE
  - Jellyfin + Navidrome : HTTPS public (Caddy + DuckDNS + Let's Encrypt)
  - qBittorrent (interface) + SSH : réseau local + Tailscale UNIQUEMENT
  - Défense en profondeur : seuls 80/443 ouverts ; HTTPS ; compte admin
    Jellyfin limité au réseau local + compte non-admin pour l'extérieur ;
    fail2ban ; mises à jour régulières.

11.0 Principes (trajet d'une requête depuis la 4G)
  1. DNS : DuckDNS traduit xxx.duckdns.org -> IP publique de la Livebox.
     L'IP publique Orange peut changer -> DNS DYNAMIQUE : un conteneur
     prévient DuckDNS toutes les 5 min (preuve d'identité = token).
  2. NAT : toute la maison partage UNE IP publique ; la box jette ce qui
     arrive de l'extérieur, sauf règle de REDIRECTION DE PORT explicite.

     Caddy). Preuve de contrôle du domaine = challenge HTTP-01 sur le
     port 80 -> c'est pour ça que 80 est ouvert aussi.

Principes :
  - Tailscale = VPN "maillé" (mesh) basé sur WireGuard : chaque appareil
    inscrit (le "tailnet") parle DIRECTEMENT aux autres, chiffré de bout
    en bout. Le serveur de coordination de Tailscale ne fait que
    distribuer les clés publiques et les adresses ; s'il n'y a pas de
    chemin direct, un relais (DERP) transporte des paquets restant chiffrés.
  - Traversée de NAT : aucun port à ouvrir sur la Livebox.
  - Adresses 100.x.y.z (plage 100.64.0.0/10 dite "CGNAT", réservée, qui ne
    se mélange pas avec 192.168.x.x) ; MagicDNS donne un nom à chaque appareil.
  - Installé sur l'HÔTE (pas en conteneur) : il doit donner accès à SSH
    et à tout le serveur.
  - Route "sous-réseau" 192.168.1.28/32 annoncée par le serveur : les
    appareils du tailnet joignent 192.168.1.28 MÊME HORS DE LA MAISON ->
    http://192.168.1.28:8080 (qBittorrent) marche partout, sans changer
    compose.yaml (le port reste lié à 192.168.1.28, jamais exposé à
    internet). /32 = UNE seule adresse, pas tout le réseau maison.
